=====================================================
 Apimetro — Guía de Base de Datos y Comandos Make
 Autor: Hernán Galileo Cabrera Garibaldi
 Última actualización: 2026-04
=====================================================

Este archivo documenta todos los comandos del Makefile relacionados con la
base de datos y los entornos Docker: qué hacen, cuándo usarlos y qué
implicaciones tienen sobre los datos y el esquema.

=====================================================
 ARQUITECTURA DE ENTORNOS
=====================================================

El proyecto soporta tres entornos independientes. Cada uno tiene:
  - Su propio volumen Docker (los datos NO se comparten entre entornos)
  - Sus propias credenciales (.env.dev / .env.qa / .env.main)
  - Su propia red Docker interna
  - Puertos distintos para no colisionar con PostgreSQL local

  ENTORNO   API (host)   DB (host)   GIN_MODE   AutoMigrate
  -------   ----------   ---------   --------   -----------
  DEV       :8080        :5433       debug      Solo si DB_HOST=localhost
  QA        :8081        :5434       debug      Solo si DB_HOST=localhost
  MAIN      :8082        :5435       release    Desactivado (usa init.sql)

NOTA: El puerto 5432 del host queda libre para tu PostgreSQL local nativo.


=====================================================
 EXTENSIONES DE BASE DE DATOS
=====================================================

El archivo db/init/init.sql instala las siguientes extensiones al crear
el contenedor por primera vez:

  postgis            — Soporte de tipos geométricos (Point, LineString,
                       MultiPolygon, etc.), funciones espaciales (ST_AsGeoJSON,
                       ST_DWithin, ST_Intersects, ST_Length, ST_Union) e índices
                       GiST para búsquedas espaciales eficientes.

  postgis_topology   — Soporte de topología vectorial (requerida como dependencia
                       de postgis y para análisis de conectividad futuros en el
                       esquema plutarco).

IMPORTANTE: Si agregas una nueva extensión a la DB local, ejecuta
'make db-sync' y actualiza este archivo.


=====================================================
 ESQUEMAS
=====================================================

  public     — Esquema principal. Contiene todas las tablas de transporte
               actualmente en uso por la API.

  plutarco   — Esquema para datos geoespaciales del INEGI usados por VFT
               (motor de Valor de Flujo de Transporte).

               Tablas:
                 plutarco.agebs        — AGEBs urbanas + Censo 2020. 6 estados
                                         de la macrometrópoli (~11,787 polígonos).
                 plutarco.calles       — Red vial CDMX (175,540 segmentos).
                 plutarco.uso_suelo    — Uso de suelo y vegetación (INEGI 1993).
                 plutarco.curvas_nivel — Isohipsas (INEGI Cartas Topográficas).
                 plutarco.afluencia_linea — Afluencia mensual por línea (Issue #39).
                 plutarco.catalogo_homologacion — Mapeo nombre CSV → linea_id.

               Cargado por: ETL/DataCharge/LoadAgebs.py, LoadPlutarcoGeo.py,
                            LoadAfluencia.py (ver sección ETL más abajo).
               El rol apimetro_read tiene permisos SELECT sobre este esquema.

=====================================================
 SEGURIDAD — ROL apimetro_read
=====================================================

La API de Go se conecta con el rol 'apimetro_read', que tiene ÚNICAMENTE
permisos de SELECT sobre los esquemas public y plutarco. Este rol es creado
automáticamente por db/init/roles.sh al inicializar el contenedor.

  Permisos de apimetro_read:
    - CONNECT a la base de datos
    - USAGE en esquemas public y plutarco
    - SELECT en todas las tablas actuales y futuras (via DEFAULT PRIVILEGES)
    - SIN permisos de INSERT, UPDATE, DELETE ni DDL

El usuario administrador (POSTGRES_USER en .env.*) es el único con permisos
completos y solo lo usa Docker internamente para inicializar la DB.
NUNCA expongas las credenciales del administrador en la API.


=====================================================
 COMANDOS MAKE — REFERENCIA COMPLETA
=====================================================

------------------------------------------------------
 make docs
------------------------------------------------------
QUÉ HACE:
  Ejecuta ~/go/bin/swag init para regenerar los archivos de documentación
  Swagger en cmd/docs/ (docs.go, swagger.json, swagger.yaml).

CUÁNDO USARLO:
  - Después de modificar cualquier anotación @Summary, @Param, @Success, etc.
    en los archivos de cmd/pkg/routes/
  - Después de agregar o modificar structs en cmd/pkg/models/
  - Se ejecuta automáticamente como prerequisito de dev, build y docker-*

IMPLICACIONES:
  - Sobreescribe cmd/docs/ completamente. No editar esos archivos a mano.
  - No afecta la base de datos ni los contenedores.

------------------------------------------------------
 make dev
------------------------------------------------------
QUÉ HACE:
  1. Ejecuta 'make docs' (actualiza Swagger)
  2. Lanza ~/go/bin/air para correr la API con hot-reload

CUÁNDO USARLO:
  Desarrollo local SIN Docker. Requiere que PostgreSQL esté corriendo en
  localhost:5432 con la base db_apimetro.

IMPLICACIONES:
  - La API corre en http://localhost:8080
  - Ejecuta AutoMigrate de GORM (crea/altera tablas si hay cambios en modelos)
  - Air reconstruye el binario automáticamente al detectar cambios en .go

------------------------------------------------------
 make build
------------------------------------------------------
QUÉ HACE:
  1. Ejecuta 'make docs'
  2. Compila el binario en bin/apimetro usando go build

CUÁNDO USARLO:
  Para compilar un binario local sin Docker (debugging, pruebas de release).

IMPLICACIONES:
  - No levanta ningún servidor ni contenedor.
  - El binario resultante lee variables de entorno para la conexión a DB.

------------------------------------------------------
 make clean
------------------------------------------------------
QUÉ HACE:
  Elimina: bin/, tmp/, cmd/docs/

CUÁNDO USARLO:
  Para limpiar artefactos de compilación y regenerar desde cero.

IMPLICACIONES:
  - NO afecta volúmenes Docker ni datos de la DB.
  - Los docs se regenerarán en el siguiente 'make docs' o 'make dev'.

------------------------------------------------------
 make docker-dev
------------------------------------------------------
QUÉ HACE:
  1. Ejecuta 'make docs'
  2. chmod +x db/init/roles.sh
  3. docker compose --profile dev --env-file .env.dev up --build

CUÁNDO USARLO:
  Para levantar el entorno de desarrollo completo en Docker.
  Recomendado cuando no tienes PostgreSQL instalado localmente o quieres
  un entorno idéntico al de producción.

PUERTOS:
  API  → http://localhost:8080
  DB   → localhost:5433 (conectar con pgAdmin u otro cliente)

IMPLICACIONES:
  - Primera ejecución: Docker construye la imagen de la API y crea el
    volumen pgdata_dev. PostgreSQL ejecuta init.sql y roles.sh
    automáticamente (crea esquema y rol apimetro_read).
  - Ejecuciones posteriores: el volumen ya existe, init.sql y roles.sh
    NO se vuelven a ejecutar. Los datos persisten entre reinicios.
  - La API NO ejecuta AutoMigrate porque DB_HOST=db_dev (no localhost).
  - Para cargar datos después de la primera ejecución, usa el proceso
    de inyección de seed.sql documentado al final de este archivo.

------------------------------------------------------
 make docker-qa
------------------------------------------------------
QUÉ HACE:
  Igual que docker-dev pero con el perfil 'qa' y .env.qa

PUERTOS:
  API  → http://localhost:8081
  DB   → localhost:5434

IMPLICACIONES:
  - Volumen independiente: pgdata_qa. No comparte datos con DEV ni MAIN.
  - Ideal para correr pruebas de integración y regresión antes de promover
    a producción.
  - GIN_MODE=debug para ver logs detallados de las peticiones.

------------------------------------------------------
 make docker-main
------------------------------------------------------
QUÉ HACE:
  Igual que docker-dev pero con el perfil 'main' y .env.main.
  Los contenedores tienen restart: always (se reinician con el sistema).

PUERTOS:
  API  → http://localhost:8082
  DB   → localhost:5435

IMPLICACIONES:
  - Volumen independiente: pgdata_main. NUNCA sobrescribir con datos de dev.
  - GIN_MODE=release: no se imprimen logs de rutas ni requests en consola.
  - CAMBIAR LAS CONTRASEÑAS en .env.main antes de usar en producción.
    Los valores por defecto son placeholders explícitos.
  - Los contenedores de MAIN tienen política restart:always (DEV y QA
    usan unless-stopped).

------------------------------------------------------
 make docker-down-dev / docker-down-qa / docker-down-main
------------------------------------------------------
QUÉ HACE:
  Detiene y elimina los contenedores del entorno especificado.

IMPLICACIONES:
  - Los VOLÚMENES de datos persisten (pgdata_dev, pgdata_qa, pgdata_main).
  - Para eliminar también los volúmenes: agregar la flag --volumes al
    comando docker compose correspondiente (operación destructiva).

------------------------------------------------------
 make db-sync
------------------------------------------------------
QUÉ HACE:
  Ejecuta pg_dump --schema-only desde la DB local (puerto 5432, usuario
  prueba) y sobreescribe db/init/init.sql con el esquema actualizado.
  Excluye: estaciones_backup, lineas_backup, ramales_backup, spatial_ref_sys.

CUÁNDO USARLO:
  Cuando hagas cambios manuales en la DB local (agregar columnas, crear
  nuevas tablas, modificar índices) y quieras que esos cambios queden
  reflejados en el init.sql para futuros contenedores nuevos.

IMPLICACIONES:
  - SOBREESCRIBE db/init/init.sql sin confirmación.
  - El archivo generado es solo DDL (sin datos). Para los datos usa
    el proceso de seed.sql documentado abajo.
  - REVISAR el archivo generado antes de hacer commit o usar con Docker,
    ya que pg_dump puede incluir sentencias específicas de la versión local.
  - Los contenedores existentes NO son afectados (el init.sql solo se
    ejecuta cuando se crea un volumen nuevo desde cero).


=====================================================
 PROCESO DE CARGA DE DATOS (SEED)
=====================================================

El archivo db/init/seed.sql NO está incluido en el repositorio (está en
.gitignore) porque contiene ~34 MB de datos de transporte.

Para regenerarlo desde la DB local y cargarlo en un contenedor:

PASO 1 — Generar seed.sql desde la DB local:

  PGPASSWORD=postgres pg_dump \
    --data-only --inserts --disable-triggers \
    -t lineas -t ramals -t estacions \
    -t descripcion_lineas -t descripcion_estacions \
    -t historico_operacion -t limites_territoriales \
    -h localhost -p 5432 -U prueba db_apimetro \
    > db/init/seed.sql

PASO 2 — Asegurarse de que el contenedor objetivo esté healthy:

  docker ps --filter "name=apimetro_db_dev"

PASO 3 — Inyectar en el contenedor DEV (usa el usuario administrador):

  PGPASSWORD='Dev_Adm1nP4ss!2024' psql \
    -h localhost -p 5433 \
    -U admin_apimetro -d db_apimetro \
    -v ON_ERROR_STOP=1 \
    -f db/init/seed.sql

  Para QA (puerto 5434):
  PGPASSWORD='QA_Adm1nP4ss!2024' psql \
    -h localhost -p 5434 \
    -U admin_apimetro -d db_apimetro \
    -v ON_ERROR_STOP=1 \
    -f db/init/seed.sql

PASO 4 — Verificar conteos:

  PGPASSWORD='Dev_Adm1nP4ss!2024' psql \
    -h localhost -p 5433 -U admin_apimetro -d db_apimetro -t -c "
    SELECT relname, n_live_tup
    FROM pg_stat_user_tables
    WHERE schemaname = 'public'
    ORDER BY n_live_tup DESC;"

CONTEOS ESPERADOS (abril 2026):
  estacions             22,878
  ramals                   693
  historico_operacion      690
  limites_territoriales    553
  lineas                   317
  descripcion_lineas         0
  descripcion_estacions      0

NOTA: La flag --disable-triggers en pg_dump genera sentencias
SET session_replication_role = replica; en el seed.sql, lo que
desactiva las FK durante la carga. Esto requiere que el usuario que
inyecta tenga privilegios de superusuario (admin_apimetro los tiene).
NUNCA usar apimetro_read para inyectar datos.

=====================================================

El archivo db/init/seed_plutarco.sql NO está en git (.gitignore).
Contiene los datos de las 4 tablas del esquema plutarco en formato COPY.
Tamaño: ~109 MB. Generado con pg_dump desde la DB DEV.

PARA GENERAR seed_plutarco.sql (desde DB DEV local):

  PGPASSWORD='Dev_Adm1nP4ss!2024' pg_dump \
    --data-only --schema=plutarco --disable-triggers \
    -h localhost -p 5433 \

PARA APLICAR EN UN ENTORNO NUEVO:

  PASO 1 — Asegurarse de que init_plutarco.sql ya fue ejecutado:
    PGPASSWORD='...' psql -h localhost -p <PUERTO> \
      -U admin_apimetro -d db_apimetro \
      -f db/init/init_plutarco.sql

  PASO 2 — Inyectar los datos:
    PGPASSWORD='Dev_Adm1nP4ss!2024' psql \
      -h localhost -p 5433 \
      -U admin_apimetro -d db_apimetro \
      -v ON_ERROR_STOP=1 \
      -f db/init/seed_plutarco.sql

CONTEOS ESPERADOS (6 tablas):
  calles                  175,540
  agebs                    11,787
  uso_suelo                 6,879
  curvas_nivel              2,661
  afluencia_linea           (varía según datos cargados)
  catalogo_homologacion     ~111 (variantes de nombres CSV)

INTEGRIDAD VERIFICADA (2026-06-05):
  - 0 geometrías nulas en las 4 tablas
  - 0 geometrías inválidas (ST_IsValid)
  - 0 registros con SRID != 4326
  - 0 atributos críticos nulos
  - agebs: todas las entidades en rango (09,15,17,21,22,29)
  - calles: 100% cobertura CDMX (cve_ent='09')

DIFERENCIAS VS seed.sql (esquema public):
  - seed.sql usa --inserts (compatibilidad). seed_plutarco.sql usa COPY

    pueden eliminarse del equipo local sin perder la capacidad de
    replicar el entorno.

=====================================================
 CORRECCIONES DE CALIDAD DE DATOS (HISTORIAL)
=====================================================

Las siguientes correcciones se aplicaron manualmente sobre la DB. Deben
repetirse al construir un volumen nuevo desde cero (después de cargar el seed).

------------------------------------------------------
 [2026-06-05] Backfill longitud/latitud en estacions (Issue #35)
------------------------------------------------------
PROBLEMA:
  Las 22,878 estaciones tenían longitud=NULL y latitud=NULL. La columna
  geom (PostGIS Point SRID 4326) sí estaba poblada. La migración GTFS
  que introdujo ambas columnas no incluyó el backfill post-inserción.
  El endpoint CRUD /movilidad/:sistema/estacion devolvía "longitud":0,
  "latitud":0 en todas las estaciones (bug silencioso de presentación).
  El endpoint GeoJSON no estaba afectado (lee directamente desde geom).

SOLUCIÓN APLICADA EN DEV (2026-06-05):
  UPDATE public.estacions
  SET
    longitud = ST_X(ST_Transform(geom::geometry, 4326)),
    latitud  = ST_Y(ST_Transform(geom::geometry, 4326))
  WHERE geom IS NOT NULL;
  → 22,878 filas actualizadas. Rango resultante:
    longitud: -99.6950 a -98.9199
    latitud:  19.1331 a 19.7624

PARA APLICAR EN PRODUCCIÓN:
  docker exec apimetro_db_prod psql -U admin_apimetro -d db_apimetro -c "
  UPDATE public.estacions
  SET longitud=ST_X(ST_Transform(geom::geometry,4326)),
      latitud=ST_Y(ST_Transform(geom::geometry,4326))
  WHERE geom IS NOT NULL;"

NOTA PARA FUTUROS SEEDS:
  Al regenerar seed.sql desde la DB local con datos correctos, el backfill
  quedará embebido en los INSERTs. No será necesario re-ejecutar el UPDATE.

CÓDIGO ELIMINADO:
  cmd/pkg/controller/utils/Estacion/FormatterEstacions.go — función
  ConvertEstacionToJson() era código muerto (definida pero nunca llamada).
  Usaba est.Longitud/est.Latitud para construir GeoJSON, pero el GeoJSON
  real se genera en GeoJsonEstacion.go vía ST_AsGeoJSON(geom) directamente.

CONSTRAINT AÑADIDO (misma sesión):
  ALTER TABLE public.estacions
  ADD CONSTRAINT chk_coords_consistency
  CHECK (
      (longitud IS NULL AND latitud IS NULL AND geom IS NULL) OR
      (longitud IS NOT NULL AND latitud IS NOT NULL AND geom IS NOT NULL)
  );
  Garantiza que los tres campos de coordenadas sean siempre consistentes.
  Cualquier INSERT o UPDATE que deje longitud/latitud/geom en estado mixto
  será rechazado por la DB. Ya incluido en db/init/init.sql.


=====================================================
 DATOS INCOMPLETOS O DE FUENTE NO OFICIAL
=====================================================

Las siguientes líneas tienen datos parciales o provenientes de
fuentes no oficiales. No son errores del ETL sino limitaciones
conocidas de los datos de origen. Están documentadas en la tabla
descripcion_lineas mediante el script db/init/UPDATE_TROLE_13.sql.

  SISTEMA     LÍNEAS   TIPO                DETALLE
  -------     ------   ----                -------
  TROLE       13       DATOS_INCOMPLETOS   Sin datos de paradas en la fuente
                                           GTFS (stop_times.txt vacío para TR13).
                                           El trazo geométrico existe (shape TR13_1,
                                           263 vértices, ruta tipo loop). ramals.geom
                                           conserva la geometría completa sin
                                           segmentación interestación. direction_id
                                           ausente en trips.txt; solo existe un sentido
                                           (ramal_num=1) por naturaleza de la ruta loop.

  MEXIBÚS     Todas    FUENTE_NO_OFICIAL   Paradas y trazos recolectados por OSMAN MAPS.
              (12)                         No provienen del GTFS oficial de la SEMOVI.
                                           num_estacion no está poblado; las estaciones
                                           se ordenan por fracción geográfica en el trazo.

  MEXICABLE   Todas    FUENTE_NO_OFICIAL   Paradas y trazos recolectados por OSMAN MAPS.
              (4)                          No provienen del GTFS oficial de la SEMOVI.

SCRIPT DE DOCUMENTACIÓN:
  db/init/UPDATE_TROLE_13.sql — inserta 17 registros en descripcion_lineas
  (1 TROLE 13 + 12 MEXIBÚS + 4 MEXICABLE). Ejecutar una sola vez por entorno.

  Verificar antes de ejecutar (evitar duplicados):
    SELECT dl.tipo, l.sistema, l.num_comercial
    FROM descripcion_lineas dl
    JOIN lineas l ON l.id = dl.linea_base
    WHERE l.sistema IN ('TROLE','MEXIBÚS','MEXICABLE');
